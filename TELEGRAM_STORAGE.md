# Telegram Storage Backend (Immich fork)

Immich UI + apps unchanged; photo originals are additionally backed up to a
private Telegram channel, encrypted at rest. Telegram is an off-ledger copy —
the on-disk file stays the source of truth and is restored from Telegram
automatically if it goes missing.

See `PLAN-TELEGRAM-BACKEND.md` for the design and sprint breakdown.

## How it works

```
upload ──▶ AssetCreate event ──▶ sync queue ──▶ encrypt (AES-256-GCM)
                                                      │
                                              gramjs MTProto upload
                                                      │
                                          private Telegram channel
                                                      │
                                        telegram_ref (assetId ↔ messageId)

GET /assets/:id/original ── file on disk? ── yes ──▶ serve
                                   │
                                   no ──▶ download + decrypt ──▶ serve
```

## Setup

### 1. Telegram API credentials

1. Open https://my.telegram.org → *API development tools*
2. Create an app, note `api_id` and `api_hash`

### 2. Private storage channel

Create a **private channel**, add yourself as admin, then get its id
(forward a message to `@userinfobot`, or read it from `@RawDataBot`).
Channel ids start with `-100`.

### 3. Environment

```bash
TELEGRAM_STORAGE_ENABLED=true
TELEGRAM_API_ID=1234567
TELEGRAM_API_HASH=your_api_hash
TELEGRAM_CHAT_ID=-1001234567890
# optional
TELEGRAM_SESSION_PATH=/config/telegram.session
TELEGRAM_DAILY_UPLOAD_LIMIT_MB=2048   # default; matches Telegram's own daily cap
```

Generate the encryption key once:

```bash
docker exec -it immich-server immich-admin telegram:keygen
# → TELEGRAM_VAULT_KEY=<64 hex chars>
```

Add it to the environment and **store it somewhere safe**. Losing it makes
already-uploaded files unrecoverable; changing it makes old files unreadable
unless the previous key is kept.

### 4. Create the MTProto session (once)

```bash
docker exec -it immich-server immich-admin telegram:login
```

It asks for the phone number (international format) and the login code Telegram
sends you, then writes `TELEGRAM_SESSION_PATH`. Re-run it only if the session is
revoked.

### 5. Run migrations and start

```bash
docker exec -it immich-server immich-admin migrations:run   # adds table telegram_ref
docker compose up -d
```

New uploads are backed up automatically.

## Operations

```bash
# status: connection, queue depth, today's quota usage, backed-up count
curl -H "x-api-key: $KEY" http://localhost:2283/api/admin/telegram/status

# queue every asset that has no Telegram copy yet (respects the daily budget)
curl -X POST -H "x-api-key: $KEY" http://localhost:2283/api/admin/telegram/backfill
```

Backfill is deliberately rationed: the daily budget (default 2 GB, matching
Telegram's own limit) stops the queue and resumes the next day. Files stay
queued in memory; a restart re-derives them from the database on the next
`backfill` call.

## Storage model notes

- **Originals are never deleted from disk.** Telegram is a backup, not a
  replacement; that keeps transcoding, ML and thumbnails on fast local storage.
- **Only the original file is backed up.** Thumbnails, previews and encoded
  videos are regenerated by Immich and stay local.
- **Encryption is per-file**: HKDF-SHA256 derives a file key from the vault key
  and a random 32-byte salt; each 1 MiB chunk uses AES-256-GCM with an
  authenticated tag, plus a header carrying the plaintext length so truncation
  is detected.
- **Restore is automatic but lazy**: it happens on the first
  `/assets/:id/original` request after the disk copy disappears.

## Limits and caveats

- One account, one channel (no multi-account rotation).
- Telegram caps uploads per account per day; the quota service enforces the
  same number so the app degrades predictably instead of being throttled.
- `FLOOD_WAIT_x` responses are retried with the server-provided delay (capped at
  15 minutes, 5 attempts) before the item is left queued.
- The session file is a credential: it grants full account access. Keep it out
  of backups published elsewhere and never commit it.
